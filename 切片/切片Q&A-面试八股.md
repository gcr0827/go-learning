## 1. 速查

```
slice header = 24 字节（ptr 8 + len 8 + cap 8）
切片是值类型；传参复制 header，底层数组共享
append 写入位置 = 起点 + len（直接覆盖，不找空位）
是否重新分配底层数组 → 由 cap 决定
```

| 扩容规则 | 条件 | 结果 |
| :--- | :--- | :--- |
| ① | `newLen > 2*oldCap` | 直接用 `newLen` |
| ② | `oldCap < 256` | 翻倍 |
| ③ | `oldCap >= 256` | `newcap += (newcap+768)/4`，循环到 `>= newLen` |
| ④ | 最后 | `roundupsize` 按内存块向上取整 |

**实测 cap 序列**

```
[]int :  1, 4, 8, 16, 32, 64, 128, 256, 512, 848, 1280, 1792, 2560, 3408, 5120
[]byte:  1, 32, 64, 128, 256, 512, 896, 1408, 2048, 3072, 4096
```

> 两个要点：**初始 cap 不同**（`[]int`=4，`[]byte`=32）；**256 之后不是 2 的幂**（848/1280/896）。

## 2. 基础

**Q1 切片 vs 数组**

| 维度 | `[5]int` | `[]int` |
| :--- | :--- | :--- |
| 长度 | 类型的一部分，固定 | 动态 |
| 大小 | 40 字节 | **24 字节** |
| 传参 | 复制整个数组 | 复制 header |

**Q2 各种初始化的 len/cap**

| 写法 | len | cap | nil |
| :--- | :--- | :--- | :--- |
| `var s []int` | 0 | 0 | **true** |
| `[]int{}` | 0 | 0 | false |
| `make([]int, 3)` | 3 | **3** | false |
| `make([]int, 3, 10)` | 3 | 10 | false |
| `make([]int, 0, 10)` | 0 | 10 | false |

- **企业级点**：接口返回空列表用 `make([]T, 0)`，否则 `json.Marshal` 是 `null` 不是 `[]`
- **预分配点**：`make([]T, 0, n)` 避免反复扩容（`[]int` 涨到 3408 容量中间扩容 **14 次**）

**Q3 值传递还是引用传递？**

> 1. Go 中**所有参数都是值传递**
> 2. 切片是**值类型**，header（ptr/len/cap）传参时**被复制**
> 3. 但复制的 header 仍指向**同一个底层数组**，所以有共享现象

❌ 别说「切片是引用类型」。

## 3. 共享底层数组（最高频）

**Q4 `b := a[1:3]; b = append(b, 99)`，`a` 变成什么？**

**答**：`[1 2 3 99 5]`

```
数组 a:   [ 1 ][ 2 ][ 3 ][ 4 ][ 5 ]
索引:       0    1    2    3    4
                 └────┬────┘
b = a[1:3]:      起点=idx1, len=2, cap=4
                写入位置 = 1 + 2 = idx3
                idx3 在 a 眼里是元素 4 → 被覆盖成 99
```

`b` 的 cap=4（够用）→ append **不扩容** → 直接写进 a 的地盘。

**Q5 `a[1:3]` 的 cap 为什么是 4？**

cap 从切片**起点算到底层数组末尾**，不是算到 len 结束。起点 idx1 → 末尾 idx4，共 4 格。

**Q6 `a[1:3:3]` 有什么用？**

第三个参数**限制新切片的 cap**：

| 写法 | len | cap | append 后 a |
| :--- | :--- | :--- | :--- |
| `a[1:3]` | 2 | **4** | ❌ 被污染 → `[1 2 3 99 5]` |
| `a[1:3:3]` | 2 | **2** | ✅ 不变 → `[1 2 3 4 5]` |

cap 被限制成 2 → `len+1=3 > cap=2` → 必须分配新数组 → 原数组安全。

**解耦手段**：`a[low:high:max]` / `copy(dst, src)` / `slices.Clone(a)`

## 4. append 机制

**Q7 append 写在哪？**

> **写在「起点 + len」的位置，直接覆盖 —— 不检查那格有没有数据。**

```go
if len(s)+1 <= cap(s) {     // cap 够
    s.array[s.len] = v      // 覆盖「起点+len」
    s.len++
    return s
}
// cap 不够 → malloc 新数组 → copy → 写入
```

cap 只决定「要不要换地」，不决定「写在哪」。

**Q8 append 为什么必须有返回值？**

**Go 是值语义，函数内改不了调用者的 `len` 字段。**

```
[函数外] len=3 cap=10
[函数内] append 后 len=4 cap=10   ← 只有副本变了
[函数外] len=3 cap=10             ← 外部没变
```

所以 `s = append(s, ...)` 这个赋值是必须的。

**Q9 cap 足够时 append 会分配新数组吗？**

**不会，但仍返回新 header（因为 len 变了）。**
证据：`make([]int,3,10)` + append 后 `&s[0]` 前后相同，len 从 3 变 4。

**Q10 函数内 append 了，外部能看到那个元素吗？**

```go
func f(s []int) { s = append(s, 1000) }
s := make([]int, 3, 10)
f(s)
fmt.Println(s[:cap(s)])   // [0 0 0 1000 0 0 0 0 0 0]  ← 能看到
```

**1000 确实写进了底层数组**，只是外部 len 没更新，「够不着」它。
**危险后续**：再 `append(s, 999)` → **999 覆盖了那个 1000**（实测 `[999 2 3 999]`）。

## 5. ⚠️ 高频误区（重点）

| # | ❌ 错误说法 | ✅ 正确 | 依据 |
| :--- | :--- | :--- | :--- |
| 1 | append 往「下一个**空位**」写 | 往「起点+len」写，**直接覆盖**，不检查有无数据 | Q4 |
| 2 | 扩容是「**2 倍**」 | 仅 `cap < 256` 翻倍；`>= 256` 走 `newcap += (newcap+768)/4` | Q11 |
| 3 | 切片是「**引用类型**」 | 切片是**值类型**，header 是值（24B），内部持有指针 | Q8 |
| 4 | cap 不够才返回新 slice | **总是返回新 header**（cap 够时也返回，因 len 变了） | Q9 |
| 5 | `_ = append(s, x)` 无副作用 | **数据已写进共享底层数组**，是隐蔽 bug | Q10 |
| 6 | `a[1:3]` 的 cap = 2 | cap 从起点算到**数组末尾** = **4** | Q5 |

## 6. 扩容（源码级）

**Q11 扩容规则？（`nextslicecap`，slice.go L326）**

```go
newcap := oldCap
doublecap := newcap + newcap

if newLen > doublecap {        // ① 需要的比翻倍还大 → 直接用 newLen
    return newLen
}
const threshold = 256
if oldCap < threshold {        // ② 小容量 → 翻倍
    return doublecap
}
for {                          // ③ 大容量 → 平滑过渡到 ~1.25x
    newcap += (newcap + 3*threshold) >> 2   // = newcap + (newcap+768)/4
    if uint(newcap) >= uint(newLen) { break }
}
// 之后 growslice 里还有 roundupsize（内存块向上取整）
```

**设计意图**：核心权衡是**扩容次数（时间） vs 内存浪费（空间）**。

| 规则 | 目的 |
| :--- | :--- |
| ① 按需 | 避免反复翻倍复制（一次性大批量） |
| ② 翻倍 | 小容量时减少扩容次数（浪费的绝对值小） |
| ③ ~1.25× | 大容量时减少内存浪费（翻倍太奢侈） |

**Q12 规则①的实测证据**

| 初始 cap | append | 新 len | 新 cap | 2×cap | 走哪条 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 8 | 1000 | 1008 | 1024 | 16 | ① 按需 |
| **8** | **16** | **24** | **24** | 16 | **① 按需**（既非 16 也非 32） |
| 256 | 100 | 356 | 512 | 512 | ② 翻倍 |
| 1024 | 100 | 1124 | 1536 | 2048 | ③ 1.25× |

**Q13 为什么 cap 「不整」（848、896）？**

规则③的公式 + `roundupsize` 内存对齐叠加。
例：`512 → 832`（公式）→ `832×8=6656` → 对齐到 6784 → **848**。

面试不必手算，说出「256 以上约 1.25×，且会做内存对齐」即可。
